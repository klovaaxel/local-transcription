### A correction to a claim in the earlier draft

The previous pass asserted caption events arrive "roughly 1-2 per second during
speech", and built the DATA-1 severity argument on that rate. **Re-reading
`asr_engine.dart`, that rate is not supported by the code.** `emitCaption` fires
from only two places:

- `consumeVad()` (`lib/asr/asr_engine.dart:196-208`), once per VAD segment the
  detector closes. The VAD is configured with `minSilenceDuration: 0.4` and
  `minSpeechDuration: 0.3` (`:269-272`), so a segment is only emitted after
  ≥0.4 s of silence — in continuous speech that is a few per minute, not a few
  per second.
- the rolling-window decode at `:226-233`, once per `_hopSamples` = 15 s
  (`:130`), as a `partial` rather than a commit.

So the real rate during a lecture is on the order of **a few events per ten
seconds to a few per minute**, depending on how much the teacher pauses. The
DATA-1 conclusion is unchanged and in fact better supported by the corrected
figure, because the argument is not about the rate — it is about each event
costing O(total corpus). See below.

## Findings

### P0 — DATA-1 — `index.json` is a full copy of the corpus, rewritten on every caption

`lib/data/lecture_session.dart:40`, `:45-46` · `lib/data/session_store.dart:28-55`
· `lib/app_state.dart:317`

**Impact.** This is the most urgent finding in the review, because of who the
app is for. It ships to real teachers who accumulate **hundreds of lectures over
a year or more**. The storage cost of this design grows with the user's history,
and the write frequency grows with speech, so the app gets monotonically worse
the longer it is used — on the exact device that is also doing the local compute.

`LectureSession.toJson` (`lib/data/lecture_session.dart:40`) serialises
**both** `transcript` and `liveCaptions` (`:45-46`). Those are the same text:
`displayTranscript` (`:33-38`) prefers `transcript` and falls back to
`liveCaptions`, and during a live recording `liveCaptions` is the only one
populated. So `index.json` is not a manifest. It is a second complete copy of
every lecture the user has ever recorded, and the full session is *already* being
written to its own `session.json` (`lib/data/session_store.dart:52-54`). The
architecture is half-built: the index re-contains what it should point at.

The arithmetic, for a 45-minute lecture:

| | |
|---|---|
| Transcript | ~50,000 chars |
| In the index | ×2 (`transcript` + `liveCaptions`), JSON-escaped, and written **indented** (`:74`) |
| Per lecture | **~100 KB** |
| At 300 lectures | **~30 MB, in one JSON file** |

And that 30 MB is not read once. `SessionStore.upsert` (`:42`) calls `list()`,
which `jsonDecode`s the whole file (`:33`), mutates one entry, then
`_writeIndex` (`:71-77`) re-`jsonEncode`s and rewrites **all** of it. Each
caption event is therefore a full ~30 MB decode plus a full ~30 MB encode on the
main isolate — ~60 MB of JSON work, twice the index size, per event.

`lib/app_state.dart:317` calls `unawaited(store.upsert(current))` from the
caption subscription, on **every caption event** for the whole recording. Over a
45-minute lecture at a few events per ten seconds that is on the order of 100
events, i.e. **~6 GB of JSON churn per lecture** at 300 lectures; even at 30
events it is ~1.8 GB. It lands on the main isolate, on top of the 20 Hz rebuild
storm from PERF-5, and it competes with the ASR isolate for cores.

The single-line summary: **the write cost of the session store is O(corpus size),
and it is paid once per caption event.** Per-event cost is linear in the number
of lectures the user has, which is why this is a P0 and why it gets worse every
term rather than staying constant.

**Resolved 2026-10-02 — measured, not estimated.** The figures above were
derived from constants; these come from a real 300-lecture corpus on disk.

| | before | after |
|---|---|---|
| `index.json` | **28.75 MB** (98.1 KB/lecture) | **112 KB** (373 B/lecture) — **99.6% smaller** |
| one caption event | ~57.5 MB of JSON decode + encode | **2.5 KB appended** |
| migration | 29.87 MB legacy index | 109.4 KB manifest, backup kept |

The `preview` is why the row is 373 bytes rather than ~120: each row carries the
110-character snippet the card renders. That snippet is *why* the old index had
to carry full transcripts — `home_page.dart` fell back to the transcript when a
lecture had no brief yet — so it is now derived at write time instead. The home
screen renders `entry.preview` now and is pixel-identical; confirmed in the
re-render.

The review's guess of "~50 KB at 300 lectures" was out by 2.2x, in the harmless
direction.

**Evidence.**

- `lib/data/lecture_session.dart:40-50` — `toJson` emits `transcript` and `liveCaptions`.
- `lib/data/lecture_session.dart:33-38` — `displayTranscript` shows they are the same text.
- `lib/data/session_store.dart:28-40` — `list()` `jsonDecode`s the whole index.
- `lib/data/session_store.dart:42-55` — `upsert` = `list()` → mutate → `_writeIndex` → `session.json`.
- `lib/data/session_store.dart:71-77` — `_writeIndex` re-encodes and rewrites everything, indented.
- `lib/data/session_store.dart:52-54` — the per-session `session.json` that already holds the full session.
- `lib/app_state.dart:317` — `unawaited(store.upsert(current))`, on every caption event.
- `lib/app_state.dart:309-318` — the whole handler is three lines: mutate, `notifyListeners`, upsert.

**Fix (decided).** Make `index.json` a lightweight manifest and move the bulk
to where it already belongs. See *Decision 1 — storage redesign* below for the
field list, the migration, and the `preview` constraint that shapes it.

Note for whoever implements this: `app_state.dart:317` is the **only**
fire-and-forget `store.upsert` in the codebase. Every other call site awaits it,
and every other call site is a state transition — `:304` (recording starts),
`:364`/`:394` (recording stops), `:412`/`:429` (transcription), `:441`/`:495`
(brief). That is exactly the shape the manifest design wants, and it means the
hot path can be deleted outright rather than made safe.

### DATA-2 — Non-atomic concurrent read-modify-write of `index.json`

`lib/app_state.dart:317`, `lib/data/session_store.dart:42`, `:71-77`

This is the original DATA-1, preserved. It is a *different* problem from DATA-1
and needs a *different* fix, so it gets its own ID.

`writeAsString` (`:73`) is not atomic: it truncates and writes in place. There is
no temp-file-plus-rename anywhere in `session_store.dart`, no lock, and no
serialised write queue. `upsert` is an unguarded read-modify-write, and
`app_state.dart:317` calls it `unawaited`, so two caption events landing close
together genuinely can interleave: both `await list()`, both mutate their own
copy, both write. The loser's change is dropped, or two concurrent
`writeAsString` calls to the same path tear the file. Losing a lecture is the
worst available failure for this app.

**Impact.** Low probability per event, catastrophic when it lands, and it gets
more likely as the index grows because each write takes longer.

**Fix.** A serialised write queue plus write-to-temp + rename. Note that the
manifest design in Decision 1 removes the high-frequency writes that make this
interleaving likely, but it does not remove the race — `delete`, and the
remaining state-transition upserts, still go through the same unguarded path.

## Interrupted recordings

Four findings, all found after the original review and none of them in that
document. The through-line: **this app has no story for a process that dies
mid-lecture**, and on the local backend that story ends in silent data loss.

### INTR-1 — No crash reconciliation exists anywhere

`lib/app_state.dart:81-95`, `lib/features/home/home_page.dart:156`

**Impact.** A session left with `status: SessionStatus.recording` by a killed
process is never reconciled, and it displays **"Spelar in" forever**.

`LectureAppState.init()` (`:81-95`) calls `store.list()` (`:83`) and nothing
else. Grepping the whole app, `SessionStatus.recording` is written in exactly
one place — `app_state.dart:301`, when a recording starts — and is cleared in
one, `active = null` at `:397`, when it stops cleanly. Nothing at launch looks
for sessions stuck in that state.

And the orphans accumulate, because the check that would stop a new recording is
absent too: `active` is null on launch (nothing in `init()` sets it), and
`HomePage`'s record button is gated only on `state.busy`
(`home_page.dart:38`). So the teacher can immediately start another lecture,
which is exactly what most people will do after their phone died mid-class. Over
a year of use, the home list fills with lectures that say they are being
recorded.

**Evidence.**

- `lib/app_state.dart:81-95` — `init()` loads and renders; no reconciliation step.
- `lib/app_state.dart:301` — the only write of `SessionStatus.recording`.
- `lib/app_state.dart:397` — `active = null` on clean stop only.
- `lib/app_state.dart:175` — the only other *read* of the state, an update-check skip.
- `lib/features/home/home_page.dart:154-163` — `_statusLabel` renders `'Spelar in'` for it.
- `lib/features/home/home_page.dart:38` — record button gated on `busy` alone.

**Fix (decided).** Reconcile at launch: any session with
`status == SessionStatus.recording` is by definition not being recorded, because
`active` is null. Repair the header (INTR-2), fold in any stray caption log
(Decision 1), and settle the status.

### INTR-2 — The local ASR path bypasses `wav_format.dart`, so a killed recording transcribes to nothing

`lib/asr/asr_engine.dart:293-297` · `lib/asr/wav_sink.dart:17-21`, `:28-37` ·
`lib/asr/wav_format.dart:81`, `:105-109`

**Impact: silent data loss, today, on the default backend.**

`WavFileSink.open()` writes its header with `dataBytes: 0`
(`lib/asr/wav_sink.dart:20`) and only patches the real size in `close()`
(`:28-37`, reopening with `FileMode.append` and rewriting the first 44 bytes). A
killed recording never reaches `close()`, so the file on disk carries a header
declaring **zero** bytes of audio, followed by tens of megabytes of PCM.

The file-transcription path then reads it at `lib/asr/asr_engine.dart:295`:

```dart
case 'file':
  captions.clear();
  final wave = sox.readWave(message['path'] as String);
```

`sox.readWave` trusts the declared length. A header saying zero means zero
samples, so `transcribeWindows` gets an empty buffer, decodes nothing, and
returns an empty transcript — with no error, no warning, and a session that
looks successfully transcribed. The teacher's lecture is still on disk in PCM
form and the app reports it as empty.

**The fix already exists, and it is already correct.** `parseWavHeader`
(`lib/asr/wav_format.dart:81`) handles exactly this case, and its own doc comment
says so (`:76-80`): *"`data` is the last chunk a recorder writes, so its declared
length can be zero or stale after a crash; callers pass `[fileLength]` and the
rest of the file is treated as audio in that case."* The fallback is at
`:105-109`:

```dart
final declared = size;
final available = fileLength - body;
final length = declared > 0 && declared <= available
    ? declared
    : (available > 0 ? available : 0);
```

`readWavInfo` (`:124-133`) is the async wrapper that feeds it a real
`fileLength`. And it is not untested: `test/wav_chunker_test.dart:107-117` is
literally named *"a truncated data size falls back to the rest of the file"*,
writes four zero bytes over the declared length, and asserts the full duration
comes back. (Read, not run — see the honesty section.)

The asymmetry is the sharpest part. **The cloud path already recovers
correctly**, because `CloudTranscriber` goes through `WavChunker`
(`lib/asr/cloud_transcriber.dart:35`), which calls `readWavInfo`
(`lib/asr/wav_chunker.dart:26`) and puts a **fresh, correct header** in front of
every part it emits (`wav_chunker.dart:74-79`). So the same crashed recording
survives on cloud and is destroyed on local — purely as a function of which
backend is configured. `asr_engine.dart:295` is the **only** call site in `lib/`
that reads a WAV without going through `wav_format.dart`.

**Evidence.**

- `lib/asr/wav_sink.dart:17-21` — `open()` writes `_header(0)`.
- `lib/asr/wav_sink.dart:28-37` — `close()` is the only place the size is patched.
- `lib/asr/asr_engine.dart:293-297` — `case 'file'` → `sox.readWave` → empty buffer → empty transcript.
- `lib/asr/wav_format.dart:76-80`, `:105-109` — the stale/zero-length fallback, already written.
- `lib/asr/wav_format.dart:124-133` — `readWavInfo`, the async wrapper.
- `test/wav_chunker_test.dart:107-117` — existing regression test for the crash case.
- `lib/asr/cloud_transcriber.dart:35` + `lib/asr/wav_chunker.dart:26`, `:74-79` — why cloud survives.

**Fix (decided, ships first and alone).** Move the local path onto
`readWavInfo` and read windowed byte ranges out of the `data` chunk instead of
loading the file — which also fixes INTR-3. Reuse the header repair the chunker
already relies on; do not write a second one.

One honest caveat to carry into the commit: **the repair is only reachable if the
user taps the orphan card**, and until INTR-1 lands that card lies about its own
state ("Spelar in"). So the fix is correct and testable on its own, but it is not
yet discoverable by a teacher who does not go looking. That is the reason for the
ship order in Decision 5, not a reason to defer the fix.

### INTR-3 — The same bypass wastes ~173 MB on a 45-minute lecture

`lib/asr/asr_engine.dart:295-296`, `:173-194`

**Impact.** `sox.readWave` loads the entire file and expands it to a
`Float32List` **before** any windowing happens. For a 45-minute lecture at
16 kHz mono 16-bit:

| | |
|---|---|
| WAV on disk | ~86 MB |
| Expanded to `Float32List` | **~173 MB** (2 bytes/sample → 4 bytes/sample) |
| What the windows actually need | ~1.28 MB at a time (20 s window + 5 s overlap) |

`transcribeWindows` (`:173-194`) then walks that 173 MB buffer in 20 s slices,
using 1.28 MB of it. The rest is pure overhead, held for the duration of the
transcription, on a device that is also holding the audio file and running the
recognizer.

The cloud path is bounded because `WavChunker` streams 10-minute parts
(`wav_chunker.dart:18`, `:68-87`) and never materialises the whole recording.

This is **independent of ASR model size**: a phone on the `small` tier is
affected identically, because the blowup happens before the recognizer is
involved. So this is not covered by the existing reasoning about which tier a
phone should pick.

**Evidence.** `lib/asr/asr_engine.dart:295-296` (whole-file read), `:173-194`
(windowing afterwards), `lib/asr/wav_chunker.dart:18`/`:68-87` (bounded
streaming, for contrast).

**Fix.** Same change as INTR-2 — `readWavInfo` for the layout, then read each
20 s window's byte range directly off the `File` and convert only that slice.
Peak memory becomes one window, independent of lecture length.

Whether phones actually *fail* on this is **OPEN-1**, not a conclusion.

### INTR-4 — `SessionPage` never inspects `status`, so the orphan is fully reachable

`lib/features/sessions/session_page.dart:91-103`, `:291-300`, `:349-350`

**Impact.** Worth recording because it is why INTR-2's fix is reachable at all,
and because it explains the shape of the bad experience.

`SessionPage` renders entirely off `summary`, `displayTranscript` and
`audioPath`. It never reads `session.status`. So an orphan session
(`status: recording`, no `transcript`, no `liveCaptions`, `audioPath` pointing
at a real PCM file with a zero-length header) opens to a page that looks
entirely normal: an empty brief pane, "Ingen text ännu." in the transcript pane,
and **"Transkribera om" already enabled** — because its only condition is
`audioPath != null` (`:349-350`), which is true.

**The three-step recovery path exists in the UI today.** Tap the card, press
Transkribera om, wait. It just produces nothing, silently, every time. That is
what makes this a P0 rather than a cosmetic issue: the app *appears* to offer a
way out and it does not work.

**Evidence.** `lib/features/sessions/session_page.dart:91-103` (render inputs),
`:291-300` (every section gets the same `pending` placeholder), `:349-350`
(`Transkribera om` gated on `audioPath` only).

**Fix.** No separate fix. It resolves with INTR-1 (the card stops lying) and
INTR-2 (the path stops returning nothing). Recorded here because it is the
reason those two are worth doing first.

## Decisions taken

These were settled in the follow-up session. They are decisions, not proposals,
and each records the reasoning that produced it.

### Decision 1 — Storage redesign: manifest index, full session at transitions, append-only caption log

`index.json` becomes a lightweight manifest holding only: `id`, `startedAt`,
`endedAt`, `status`, `audioPath`, a cached `title`, and a 110-character
`preview`. `session.json` holds the full session and is written **only at state
transitions**. A new append-only `captions.jsonl` in the session directory
records live caption events during recording.

**The constraint that shapes this, and it is easy to get wrong:** a manifest
cannot simply drop the transcript. `home_page.dart:105` does

```dart
final preview = session.summary?.discussed ?? session.displayTranscript;
```

and `home_page.dart:108` renders the first **110 characters** of that as the
card preview. So the home screen genuinely needs a snippet of text even when no
brief exists — a lecture that has been recorded but not yet transcribed has no
`summary.discussed` to fall back on. **That requirement is *why* the index
carries full transcripts today**, and it is a real need, not an accident. The
manifest therefore needs a **derived `preview`**, computed at write time, not
the transcript itself.

`autoTitle` is derived the same way (`lib/summarize/newsletter.dart:189`) and
should be cached into the manifest when the brief lands, so the home list does
not need the full summary to render a title.

With both in place: **the index falls from ~30 MB to roughly 50 KB at 300
lectures, with no visible change to the home screen.** The 110-char preview and
the auto-title both still render, from cached fields.

### Decision 2 — Migration is simple, not defensive

There are only a handful of beta testers. No schema-version machinery, no
migration framework, no back-compat shim: rewrite the index **once**, keep a
backup copy of the old one, and be non-destructive on first run. The
engineering effort belongs in INTR-2 instead, where it prevents actual data
loss.

### Decision 3 — Captions are persisted during recording, not buffered in memory

A killed lecture must keep its text, so caption events go to `captions.jsonl`
as they arrive rather than accumulating in `liveCaptions` and being written once
at the end.

This also **removes the hot path entirely**, which is the important second
effect: the index is written **once, at recording start**, and nothing during a
recording changes any of the fields it holds. `{id, startedAt, status:
recording}` is fixed for the duration. So caption persistence no longer touches
`index.json` at all, and `app_state.dart:317` is deleted rather than optimised.

### Decision 4 — Interrupted recordings get full recovery

Reconcile at launch (INTR-1), repair the stale header (INTR-2), fold in any
stray caption log (Decision 3). All three are needed for a coherent result: a
reconciled session that says `ready` but has no transcript because its audio was
never read is not a recovery.

### Decision 5 — Shipping unit: the WAV fix goes first, and alone

`asr_engine.dart:293-297` onto `readWavInfo` with windowed reads, as its own
commit. It is small, changes no on-disk format, needs no migration, is
independently testable, and it stops silent data loss today. Every other item
here is an improvement; this one is a bug that is losing users' lectures.

The caveat from INTR-2 travels with it: the repair is only *reachable* if the
user taps the orphan card, and that card lies about its state until INTR-1
lands. Correct but not yet discoverable. Record that in the PR rather than
implying the fix is self-service.

### Decision 6 — Brief progress and cancel: per-section, with an abort flag plus dispose

Per-section progress instead of one identical placeholder, plus a working
cancel. The cancel unwinds **at chunk boundaries** and then calls `release()` to
genuinely halt the decode.

The pipeline already has the checkpoints this needs: `onProgress?.call(step,
total)` fires before each map part (`brief_pipeline.dart:105`, `:109`, `:112`),
so an abort flag checked at those points interrupts cleanly between chunks
rather than mid-decode. The reduce phase (`:116`) needs its own check, since
`:112` fires once before it rather than per group.

**The constraint that makes this non-obvious, and it is easy to get wrong:**
`llm_llamacpp` 0.4.0 (`pubspec.yaml:47`) exposes **no cancel or stop API —
only `dispose`.** Verified in the package source, not assumed:

- `PersistentInferenceIsolate.runInference` does `yield* controller.stream`
  (`lib/src/persistent_inference_isolate.dart:145`). Its `finally` block
  (`:146-153`) closes the controller and removes the pending request **on the
  Dart side only**. It never sends a cancellation message to the helper isolate.
- Every teardown method in the package is `dispose()` — on
  `PersistentInferenceIsolate` (`:157`, which does `_helperIsolate?.kill()`),
  the repositories, the model, the loader. There is no `cancel` or `stop`
  anywhere in the public surface.

So **simply breaking out of the token stream would leave llama.cpp decoding
into a request id nobody is reading** — the Cancel button would look responsive
while the phone stayed pinned at 100% CPU. Hence the two-part design: an abort
flag checked at the checkpoints, *plus* `dispose` to actually free the CPU
(`LocalLlmSummarizer.release()` at `lib/summarize/local_summarizer.dart:96-97`
is `_repo?.dispose()`, which is what makes it effective).

Worth noting so it is not treated as a regression: **the model reload that
follows a cancel is already the per-brief cost.** `summarizeSession` builds a
fresh `LocalLlmSummarizer` on every call (`app_state.dart:471`), and
`brief_pipeline.dart:118` disposes it in a `finally`. Nothing is being cached
across briefs, so cancelling does not introduce a reload that did not already
happen.

## Open question

### OPEN-1 — Do phones actually fail on long lectures, given the ~173 MB buffer?

**Unresolved, deliberately.** INTR-3 establishes that `sox.readWave` expands a
45-minute lecture to ~173 MB of `Float32List` on the transcribing device. What
is *not* established is whether that actually causes an out-of-memory failure,
an OS kill, or nothing at all — and the answer is genuinely device- and
OS-dependent (Android's per-app limits, iOS jetsam thresholds, and how much of
the heap is already in use by Flutter itself all matter). Discussion was not
going to settle it.

**Proposed test, when a device and an SDK are both available:**

1. Record a 45-minute lecture on the slowest phone in the test set.
2. Transcribe it with the default local path (no cloud).
3. Watch peak RSS and whether the process is killed — `adb shell dumpsys
   meminfo <pkg>` sampled during, plus logcat for `lowmemorykiller` /
   `am_kill`.
4. Repeat with the `readWavInfo` + windowed-read path and compare peak RSS.

Until that runs, INTR-3's fix is justified on **memory hygiene and
length-independence**, not on a measured crash. Do not let it be justified as
"fixes the OOM" until OPEN-1 says so.

## Performance findings

Unchanged from the original pass except where noted. Still real, still
unmeasured in magnitude.

### PERF-1 — Quadratic allocation churn in the live ASR path

`lib/asr/asr_engine.dart:210`, `:321`

`pushFloats` calls `rolling = _concat(rolling, samples)` on **every PCM
callback**. `_concat` allocates a fresh `Float32List` of `a.length + b.length`,
copies all of it, then — because `rolling` is already pinned at the cap — trims
by allocating *two more* lists (`out.sublist(...)`, then
`Float32List.fromList`).

The window-decode block at `:226` reads `rolling.sublist(rolling.length -
_windowSamples)` but never shrinks `rolling`. So in steady state `rolling.length`
sits at exactly `keep = _windowSamples + _hopSamples` (`:328`) = 20 s + 15 s =
560,000 floats = 2.24 MB, which is permanently the worst case for `_concat`.

| | |
|---|---|
| Per callback | ~6.7 MB allocated and copied (3 lists, 2.24 MB each) |
| Callback rate | ~8/s at 16 kHz mono 16-bit in ~128 ms chunks (assumed) |
| Sustained | **~54 MB/s inside the ASR isolate, for the whole lecture** |
| A 45-min lecture | on the order of 140 GB of allocation and memcpy |

This runs in the ASR isolate on the recording path, so it competes with the
decoder for cores and drives GC in the one place that must not stutter.

Fix is small: trim in blocks rather than per call (only shrink once
`rolling.length > keep + margin`) and reuse one buffer with `setRange`. A
`sox.CircularBuffer` is already instantiated as `ring` at `:278` and could take
this job entirely.

### PERF-2 — Whisper thread count hardcoded to 2

`lib/asr/asr_engine.dart:261` — `numThreads: 2` for the recognizer, never
scaled. Meanwhile `app_settings.dart` selects the *large* ASR model precisely
because it counted ≥4 cores. On an 8-core desktop the app downloads a 1.8 GB
model — at roughly 3× the medium tier's compute per second of audio — and then
feeds it two threads. Straight throughput loss on the operation the user is
waiting on, and it got worse when the auto pick moved to kb-whisper-large.
Scale from `Platform.numberOfProcessors` and persist it alongside the rest of
the model selection.

Caveat before changing it: whether 2 was a deliberate mobile choice (big.LITTLE
oversubscription) or just a default nobody revisited is not recorded anywhere.
Check `feedback/quality/SCORES.md` and any phone notes before scaling, and keep
the phone default conservative regardless.

### PERF-3 — `mergeOverlappingTranscript` is O(n²) with per-call re-normalization

`lib/asr/transcript_merge.dart:8`

Two separate problems in the merge that runs on every committed caption:

1. `prevNorm` is rebuilt for the **entire accumulated transcript** on every
   merge (`:20-21`, from the `:18` split) — two `RegExp.replaceAll` per word,
   ~9,000 words, ~180 times per 45-min lecture.
2. The fallback loop at `:30-31` calls `_indexOfWords` up to `n` times; each
   scans the whole haystack and does a `sublist` **allocation inside the loop**,
   once per iteration.

Fix: cache the normalized word list on `LiveCaptionBuffer` instead of
recomputing it, compare by index offset instead of `sublist`, and search only a
tail window of `prev` — the overlap can never be far from its end.

### PERF-4 — `keyLineHints` computed twice per chunk

`lib/summarize/brief_pipeline.dart:164` and `:168` — same argument, same result,
computed twice. `keyLineHints` runs `_roughSentences`, which splits the entire
chunk on whitespace and regex-tests every word before the `maxLines` early-break
can help. Hoist to one local. Free win, no behavioural change.

### PERF-5 — 20 Hz `notifyListeners()` rebuilds the entire app

`lib/app_state.dart:741` — the input-level throttle is 50 ms (`:748`), so every
`context.watch<LectureAppState>()` consumer rebuilds at 20 Hz for the whole
recording: home list, session page, toast layer. The toast body is wrapped in
`IntrinsicWidth` (`lib/ui/soft_toast.dart:229`), which forces a second layout
pass, 20 times a second. Scope the level to just the meter (a `ValueListenable`
or its own `ChangeNotifier`) and most of this goes away.

Worth noting in light of DATA-1: this and DATA-1 share a root cause — broad,
high-frequency `notifyListeners()` from a hot path. Fixing DATA-1's write
frequency removes most of the *notification* pressure here too, so measure
after, not before.

### PERF-6 — The transcript pane builds one enormous `SelectableText`

`lib/features/sessions/session_page.dart:342`. A 45-min lecture is ~50k chars in
a single selectable text run inside a `SingleChildScrollView`; that lays out and
hit-tests one huge paragraph. Splitting on blank lines into per-paragraph
`SelectableText` (or a lazy `ListView.builder`) keeps copy-selection working and
makes the pane actually scroll.

## UX findings

### UX-1 — The brief auto-starts, but the real gap is progress and cancel (corrected)

**The original finding was overstated and is withdrawn as written.** It claimed
that opening a lecture "silently starts a multi-minute LLM job", framing it as a
surprise. Re-reading the guard at `lib/features/sessions/session_page.dart:91-95`:

```dart
if (!_askedForBrief &&
    session.summary == null &&
    session.displayTranscript.trim().isNotEmpty &&
    !state.busy &&
    session.error == null) {
```

It fires **only** for a session that has a transcript but no brief. In practice
that is two things: the post-recording push from `home_page.dart:53-62`, and the
rare case where a brief was deleted. Reopening an already-briefed lecture does
nothing, because `summary != null`. `_askedForBrief` (`:25`) also makes it
once-per-session-per-page rather than once-per-rebuild.

So the auto-fire is **well-targeted, not surprising**. The original finding
should not be used to justify removing it.

**The real remaining problem is narrower, and it still stands.** Every section of
the brief card renders one identical placeholder (`:265`, looped over
`NewsletterSummary.defaultHeadings` at `:291-300`), so the teacher cannot
distinguish a job that will take 40 seconds from one that will take ten minutes,
and there is no way to cancel. That is the gap Decision 6 closes — per-section
progress plus a cancel — and it is an interaction design problem, not a code
cleanup.

### UX-2 — No long operation is cancellable

`transcribeSession`, `summarizeSession`, `updateNow` are all `_run`-wrapped
(`lib/app_state.dart:710`) with no abort path. A 9B brief on CPU that takes ten
minutes cannot be stopped. For an app whose entire job is long local compute,
this is the most-missed feature on the list. Decision 6 covers the brief half;
transcription and update remain open.

### UX-3 — The record page cannot be escaped

`lib/features/record/record_page.dart:55-56` — `PopScope(canPop: false)` with no
abort affordance. A recording started by mistake costs a full stop-then-delete.
An "Avbryt" that discards would be a small, obvious addition.

### UX-4 — `busy` is a single global bool

`lib/app_state.dart:710` — any slow operation disables every button in the app,
including the record button on home (`home_page.dart:38`). Defensible as intent,
but it also means all buttons and the toast churn on every state change, and it
is the same coarse-grained-notification problem as PERF-5.

### UX-5 — Downloaded models cannot be deleted (found on the second pass)

Found while closing the `settings_page.dart` coverage gap. There is a section
labelled **"Lagring"** at `settings_page.dart:436`, but it contains exactly one
control: the `deleteAudioAfterTranscribe` toggle. The models — the large thing —
have no reclaim path anywhere in the app. The only `delete` calls in
`lib/asr/model_downloader.dart` are the temp file during a download (`:101`) and
a corrupt destination being replaced (`:128`).

This matters more than it looks, because the app is built to accumulate models:

- The LLM tiers are single GGUF files up to ~5.7 GB, plus an ASR model up to
  ~1.8 GB.
- **The auto pick is not stable across the app's life.** `autoLlmForDevice`
  picks a tier from the launch benchmark, and the decode probe
  (`lib/perf/llm_speed_probe.dart`) can step it down after a model has already
  been downloaded. A user who starts on the large tier and whose probe
  demotes them is left holding both, with no way to reclaim the larger.
- Beta testers switching tiers while comparing models — which is exactly what
  the tiers are for — will silently accumulate gigabytes.

So "Lagring" is the wrong section for this, and it is an easy, self-contained
fix: list the downloaded files with their sizes and offer a delete each, plus a
"free space" total. It also makes the existing cost legible — a user choosing
between a 1.3 GB and a 5.7 GB tier currently has no way to see either.

**Severity:** low-risk, high-certainty, moderate user-visible annoyance. Cheap
relative to everything else on this list.

### UX-6 — The empty state filled the whole screen (found in the first render)

This one is the exception on this list: it was invisible in the source and only
appeared once the preview harness could run (2026-10-01). `home-empty.png`
showed a card two lines of text tall stretching ~480 px down a 844 px screen —
a large blank panel that reads as a loading state or a rendering fault, and is
the first thing a new user sees.

**Cause.** `SoftPage` gives its body an `Expanded` (`soft_widgets.dart:93`), so
the body gets a *finite* max height. `_EmptyLectures` puts a `Column` inside the
card, and a `Column`'s default `mainAxisSize: MainAxisSize.max` resolves to
`constraints.maxHeight` **even under loose constraints** (`RenderFlex`), so the
column grew to fill and the card followed it.

This is why no amount of source reading caught it: the pattern is idiomatic
Flutter and looks correct everywhere else. Every other body in the app is a
scrollable, where the max height is infinite and `MainAxisSize.max` is harmless.
`_EmptyLectures` is the single non-scrollable body, so it is the single place
the default bites. Confirmed by measurement, not inspection: the card laid out
at 350×480 before the fix and 350×215 after.

**Fix.** `mainAxisSize: MainAxisSize.min` on that one `Column`, with a comment
saying why. Verified in the re-render.

**Worth carrying forward:** any future non-scrollable `SoftPage` body needs the
same treatment, and a layout test asserting a card's height would catch this
class of thing without anyone having to eyeball a PNG.

## How to verify these

Once a Flutter SDK **and** a device are available. Note that step 1 of the
sequence requires `flutter test` — it is not optional.

- **INTR-2** - **the test now exists and has never been run.**
  `test/wav_windows_test.dart` covers the crash case end to end: it writes a WAV
  with a valid header declaring `dataBytes: 0` followed by 60 s of real PCM
  (exactly what `WavFileSink.open` + a kill leaves), asserts `readWavInfo` reports
  the full `dataLength`, and asserts the reader hands back four windows
  `[20 s, 20 s, 20 s, 15 s]` whose first and last samples are the actual signal.
  It also contains a differential test that walks the **old** whole-file loop
  transcribed verbatim, with `20 * 16000` / `15 * 16000` spelled out rather than
  named, and asserts the new reader reproduces it sample for sample — so the
  geometry cannot drift without a failure. `test/wav_chunker_test.dart:107-117`
  remains the equivalent for the cloud path.
  **Two risks in that file, both from being unable to run it:** the differential
  comparison deep-matches ~1.9 M floats through matcher recursion, which may
  time out (compare a digest instead if it does); and the record comparisons
  rely on `equals` falling through to `==`, which the SDK's `_DeepMatcher` does
  not explicitly cover.
- **INTR-1** — leave a session with `status: recording` on disk, launch, assert
  it is reconciled and no longer labelled "Spelar in".
- **DATA-1** — record 20+ lectures, then assert the index size and the caption
  write rate. Peak RSS during a recording is the metric that should collapse.
- **PERF-1** — record with live captions on, and watch isolate RSS / GC in
  DevTools or `flutter run --profile`. The allocation rate should drop by
  orders of magnitude after the fix; compare against the ~54 MB/s figure above.
- **PERF-2** — transcribe the same 45-min WAV at 2 vs. 4 vs. 8 threads and
  record wall time. This is also a good corpus for `applyAsrCalibration`.
- **PERF-5** — `flutter run --profile`, DevTools performance overlay during a
  recording, watch frame times.
- **PERF-6** — open a long lecture on a low-end device, scroll the transcript
  pane.
- **OPEN-1** — the 45-minute device protocol described in the finding.
- **Q-1 / Q-2** — `LLM_PROBE=1 LLM_PROBE_RUNS=N flutter test
  test/brief_probe_test.dart`, scored against the corpus in `feedback/golden/` as
  usual. Never against kfn alone.
